# 基线归属判断

## 适用边界

先按用户需要的结论选择模式：

- **直接历史追溯**：用户问某段代码、符号或行为是谁、何时、由哪个提交引入。直接检查 Git 历史，不询问版本基线。
- **相对版本比较**：用户问问题相对某个版本是否既有、由当前改动引入或被当前改动恶化。先执行显式基线关口，再比较完整快照。

单纯判断当前或暂存代码是否满足已确认业务规则、能否消除某个问题，或解释当前行为与根因，直接检查目标代码及必要调用路径；不要求历史基线，不将定点问题扩展为归属调查。提及、讨论或修改本技能说明不构成调用。

进入相对版本比较后，先确定问题相对于权威基线的归属，再作归属相关的根因结论或修改建议。用户负责指定业务认可的基线；Agent 负责核实证据并直接作出归属结论，不能要求用户替 Agent 定性。

## 子代理调查

主代理负责选择调查模式、执行显式基线关口、控制权限与调查范围，并将实际历史取证交给子代理。直接历史追溯中的当前实现与调用链定位、`git blame`、文件历史、文本变化、重命名与合并追踪、候选提交及父提交核实，由子代理执行；相对版本比较中的完整快照、分叉与祖先关系、blob 哈希、首次出现提交、调用方与数据条件变化，以及“引入、扩大或仅触发”的证据分析，也由子代理执行。子代理只执行只读调查，按本 Skill 的最小证据集返回文件路径、符号、完整提交哈希、实际检查对象和对应事实，不得自行执行 `fetch`、`pull` 或 Git 写入。

一项不可分割的归属问题交给一个子代理端到端调查；存在相互独立的证据问题时才并行分配，并为每个子代理指定明确且不重叠的证据责任。主代理检查返回证据是否满足最小证据集，必要时定点复核决定归属的关键证据，综合作出作者归属、版本归属、因果关系、修改范围或证据不足的最终结论，并在报告中区分子代理调查结果与主代理补充复核。

子代理暂时没有返回不视为失败，按上层等待规则继续等待。子代理明确报错或终止时，可在不改变调查范围的前提下重新分配；无法启动子代理、全部子代理明确失败，或返回证据仍不满足最小证据集时，停止归属判断并报告具体证据缺口，不静默改为主代理独自完成全部调查。

## 直接历史追溯

1. 用当前文件和调用链确定需要追溯的具体符号、语句或行为，避免把父调用栈误认为实际问题实现。
2. 使用 `git blame` 定位当前行归属，再结合 `git log --follow`、`git log -S` 或 `git log -G` 追过重命名和文本变化。
3. 查看候选提交及其父提交的完整相关文件或差异，确认该逻辑在候选提交中首次出现。合并提交只搬运已有代码时，继续追到原始提交。
4. 分开报告入口代码、核心实现和后来扩大影响的改动；当前行被重写不等于当前作者最初引入了该行为。
5. 现有历史不足以穿过仓库截断、合并或重命名时，报告可追溯边界，不猜测更早作者。

## 相对版本比较的显式基线关口

每次开始一项新的相对版本比较，都必须由用户明确给出一个权威基线。用户在触发请求或后续回复中明确给出的单一基线已经完成确认，不需要再复述追问。历史上下文、默认分支、当前 `HEAD`、看似唯一的候选项或 Agent 自己的推断不能代替用户指定。

1. 用户在触发请求中明确给出一个基线时，记录其名称和本地、远端、提交、标签、版本或参考实现等身份，并直接进入调查，不得再次要求确认。
2. 用户没有给出基线时，只询问本次权威基线是什么。
3. 用户在后续消息中直接给出或更正为一个明确基线时，记录完整身份并直接进入调查，不得再次复述追问。
4. 用户给出的基线含糊或同时包含多个候选时，只说明歧义并询问一个简洁的澄清问题；获得单一明确基线后立即进入调查。
5. 用户明确指定基线前，不核实引用、不比较快照，也不作相对版本归属判断；这项限制不适用于直接历史追溯。
6. 同一项已明确指定基线的调查沿用该基线；开始新的调查或再次调用本 Skill 时需要用户重新指定，不能沿用上一次任务的基线。

## 基线关口

1. 只使用用户明确指定的 release 分支、提交、标签、版本或参考实现作为权威基线。
2. 核实所选引用实际存在，记录其提交哈希，并区分本地分支、远端跟踪分支、直接父提交、合并基线、当前 `HEAD` 和本地工作树。
3. 只使用当前已有的 Git 引用。`fetch`、`pull` 或其他会更新引用的操作需要用户另行授权。

## 比较方法

- 分别读取基线与当前版本的完整文件快照；不能只看当前代码或单个提交差异。
- 使用合并基线和提交历史确认分叉关系，再比较与现象相关的源码、配置、Schema、测试、调用方和数据条件。
- 对关键文件可比较 Git blob 哈希；哈希相同表示完整文件内容相同。
- 追踪相关逻辑首次出现的提交，并确认该提交是否属于基线祖先。
- 将代码原因与触发条件分开。当前改动主动扩大数据量、并发量、调用方、触发范围、严重程度或恢复代价时，归为当前改动扩大或恶化既有问题；仅由外部数据或测试场景暴露、相关实现没有变化时，归为当前场景触发。
- 工作树存在用户修改时，保留这些修改，并使用 `ref:path` 读取历史快照，避免把工作树内容混入基线结论。

## 版本归属结论

根据证据直接选择并陈述一种结论：

- **基线既有**：基线完整快照已经包含导致现象的实现或行为，当前改动没有改变对应路径。说明当前场景是否只是触发或放大了问题。
- **当前改动引入**：基线不具备该问题，当前改动改变了对应路径。指出首次引入的提交、关键差异和影响范围。
- **当前改动扩大或恶化**：基线已经存在问题，但当前改动增加了受影响的输入、调用方、对象或数据范围，或者提高了发生频率、严重程度、副作用及恢复代价。只报告并归因当前增量，同时说明基线问题与增量之间的因果关系。
- **证据不足**：现有快照、历史或复现条件无法区分归属。明确缺少什么证据，不猜测结论。

结论使用直接陈述，例如：

> 这是 `release/mon631` 已存在的缺陷，由 Multiple studyset 的大规模数据场景触发暴露。

不要询问用户“是否认可”由代码和历史能够确定的事实结论。用户提供或纠正基线后，重新比较受影响证据并更新结论。

## 修改边界

- 基线既有且当前改动没有扩大或恶化的问题不自动进入当前改动范围。若用户只要求判断当前改动是否引入问题，报告结论后停止修改。
- 当前改动扩大或恶化既有问题时，该增量属于当前改动范围；修复目标默认是消除当前增量，不顺带重写未受影响的基线行为。
- 用户已经明确要求修复该既有问题时，继续按其授权范围规划；否则说明修改基线行为的影响并询问是否纳入范围。
- 当前改动引入的问题优先在引入差异的职责所有者处修复，不顺带处理无关的基线问题。
- 调查请求只执行只读检查；没有明确修改授权时不得写入代码、配置、数据或 Git 状态。

## 最小证据集

直接历史追溯至少包含：

- 被追溯的入口、核心实现或行为；
- 当前行的 `blame` 归属；
- 经文件历史、文本搜索和父提交核实的首次出现提交；
- 作者、作者日期、完整提交哈希和主题；
- 后续改动只是搬运、重写，还是扩大了影响。

相对版本比较至少包含：

- 权威基线名称与提交哈希；
- 当前比较对象与提交哈希；
- 两者的分叉或祖先关系；
- 相关完整快照或 blob 是否相同；
- 问题逻辑首次出现的提交；
- 当前场景是引入原因还是触发条件；
- 该归属对修改范围的实际含义。
