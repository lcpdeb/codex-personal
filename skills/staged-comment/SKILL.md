# 暂存区提交说明

讨论或修改本技能说明不构成执行提交流程的授权。

## 工作流程

先用 `git diff --cached --name-only` 确认本次改动范围，暂不读取具体 diff。

如果没有暂存变更，用用户的语言输出一句话，说明没有可总结的暂存变更。

在阅读具体实现前，结合用户已明确的目的和必要的改动前代码，明确每个独立业务问题或需求、受影响的对象或流程、预期结果与关键约束。文档、重构等维护工作说明真实维护目的，不强行套用业务故障。已有说明充分时直接继续；缺少会改变提交目的或分类的信息时，先询问用户，澄清前不生成最终提交说明、不创建提交。

保留用户已确认的业务目的；改动内容必须每次使用 `git diff --cached --stat` 和 `git diff --cached` 重新核对，不沿用旧 diff 或旧提交说明。必要时使用 `git show HEAD:<path>` 和 `git show :<path>` 读取改动前与暂存区的相关完整代码，不把未暂存内容写入说明。

用当前暂存区实现核对已明确的业务目的，区分预期效果与代码证据能够支持的实际变化；不得从实现写法反推或替换需求。若实现与目的存在影响提交说明的实质冲突，说明具体差异并请用户澄清，澄清前不提交。本技能不增加独立方案设计或完整代码审查流程。

结合已明确的业务目的和当前暂存区 diff 生成提交说明；除所选格式需要的 TYPE 标题和正文外，不添加额外标题、前言、解释或结尾说明。

业务目的明确且提交说明与当前暂存改动相符后，立即使用生成的提交说明原文创建本地 git commit。

提交成功后，使用 `git rev-parse HEAD` 获取完整 commit hash，使用 `git branch --show-current` 获取当前分支。

如果当前不是分支状态，输出 `分支：HEAD（detached）`。

第一行 `TYPE: ...` 作为 commit subject；需要 body 时，空一行后写补充说明或其他独立主题，并保留项目符号和段落。

提交时不要改写、缩短、重命名或替换已经生成的提交说明。

提交成功后，用用户请求的语言简洁回报提交说明、commit hash 和分支。

## 业务目的、分类与格式

按已明确的业务问题或需求组织独立主题，用暂存差异核实必要影响和改动内容。提交说明应让读者知道这次改动解决什么问题或满足什么需求，不能只描述修改动作；不臆测问题、故障范围或未经验证的效果。

提交说明使用能完整表达主题的最短格式。第一行始终是 `<TYPE>: <主题>`；只有需要补充标题无法承载的背景、原因、约束、解决方式或多个必要措施时才写正文，不为满足格式重复标题内容。

- `FIX`：标题描述**改动前具体存在的问题**，说明哪个对象在什么情况下出现了什么错误及其实际影响；修复动作、实现方式和修复后的目标放在正文，以 `- ` 说明。此规则适用于主标题和后续每个 `FIX` 主题，也适用于所有输出语言。
  - 正例：`FIX: Robustness templates overwrite CT identities and drop candidate CTs`。
  - 反例：`FIX: Preserve CT identities and selections when applying robustness templates`；它描述的是修复目标，应放入正文。
- `FEATURE`、`PERF`、`REFACTOR`、`TEST`、`BUILD`、`CI`：动作型标题已完整说明交付内容时使用单行；需要区分现状或需求与做法，或者交代兼容性、约束、测量边界时再写正文。
- `DOCS`、`STYLE`、`CHORE`：默认使用说明实际动作的单行标题；只有理由或多个非显然改动对理解提交必要时才写正文，不虚构运行时或业务影响。
- `REVERT`：标题能明确撤销对象时使用单行；原因或恢复后的影响对理解提交必要时再写正文。

类型使用大写英文，后续内容和标点匹配用户请求的语言。以下是常用类型，不是封闭枚举；按实际目的选择更准确的类型，已有用户或项目类型约定时优先遵循，不因文件扩展名机械分类。

| 类型 | 分类依据 |
| --- | --- |
| FIX | 纠正已有业务错误 |
| REFACTOR | 保持业务行为，改善代码结构 |
| FEATURE | 满足新增业务需求 |
| PERF | 改善性能或资源消耗 |
| DOCS | 改善文档 |
| TEST | 改善验证覆盖或测试可靠性 |
| BUILD | 调整构建、打包或依赖 |
| CI | 调整持续集成或交付流程 |
| STYLE | 统一格式或书写风格，保持行为不变 |
| CHORE | 其他维护工作 |
| REVERT | 撤销已有变更 |

分类依据是改动目的，重构可以是实现手段：通过重构修复业务错误仍写 FIX，通过重构提供新能力仍写 FEATURE。同一主题不因采用重构手段而再拆一条 REFACTOR；只有重构具有独立目的和交付价值时才单列。

重构不虚构业务故障，新增功能不硬套错误修复。文档、测试、构建等主题写其真实使用者或工作流程的需求与影响，不虚构临床、客户或运行时影响。

示例展示不同类型所需的最短完整格式，实际内容必须结合已明确的业务目的和当前暂存差异重新生成：

```text
FIX: 无 Base Dose 的 Candidate 会错误继承 Reference 剂量

- 改为保持无剂量输入。

FEATURE: 支持多个 StudySet 参与同一次联合优化

DOCS: 删除评审中已解决的风险项
```

## 变更点拆分规则

- 先按已明确的业务目的划分高层主题，再用当前 diff 核对覆盖范围。用户可见行为、接口或数据流、配置/兼容性、测试、文档等具备独立交付意义时，分别作为主题；多个文件属于同一行为时合并为一个主题。
- 只有一个独立主题时，使用该类型所需的最短完整格式；无需 body 的主题只保留 subject。
- 有两个或以上独立主题时，主要主题作为 subject；只在该主题需要正文时补充 body。后续独立主题使用 TYPE 标题及其必要正文，主题之间空一行。
- 文档变更仅用于同步同一代码改动的说明、示例或评审结论时，归入主代码主题，不单列 `DOCS`；主主题已完整覆盖时无需额外写入提交说明。只有文档具有不同的独立交付目的时才单列 `DOCS`。
- 独立的测试或配置变更不得用泛化的一句话吞并。
- 不按文件清单或实现步骤写；压缩后会丢失独立主题时，保留必要内容。
- 生成后检查每个独立主题的业务问题或需求及对应改动均被覆盖，分类符合已明确的目的，预期结果未被写成未经验证的完成事实，内容没有重复或文件清单。逐条检查 `FIX` 标题：单独读标题应能知道改动前具体出了什么问题；若只说明本次做了什么或修复后要达到什么效果，先改写为问题陈述再提交。

## 输出规则

- 匹配用户请求的语言：提交说明和成功回报均使用用户请求的语言。
- 用业务语言描述高层问题、影响和解决方式；仅在解释解决方式必需时提及技术手段，不展开实现细节。
- 每个标题和必要正文分别使用一句简洁表述。
- 避免重复、从属或互相重叠的变更点。
- 属于同一主题的变更合并在同一个 TYPE 标题下，不重复描述问题或解决方式。
- 优先描述用户可见的问题或独立变更主题，不要写成代码操作清单；`FIX` 标题保持改动前的问题陈述，其他类型沿用各自的标题规则。
- 使用简洁的提交说明风格。
- 除非为了表达清楚必须提到，否则不要写文件名、类名或函数名。
- 提交成功后的回报格式为：英文请求使用 `Committed:`、`Commit message: <generated message>`、`Commit hash: <full hash>`、`Branch: <current branch>`；中文请求使用 `已提交：`、`提交说明：<生成的提交说明>`、`commit hash：<完整 hash>`、`分支：<当前分支>`。
