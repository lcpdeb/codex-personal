# Explain

说明所问对象的实际行为、原因、结果及改动依据。简单问题直接回答；整组代码改动按逐项确认流程推进。现有事实、明确要求和执行授权持续有效。

## 1. 业务流程与代码行为

### 业务语境与修改依据

- 所有解释性问题都围绕所问对象的实际行为展开，按理解所需的顺序连接场景、流程、原因和结果。简单问题直接解释；涉及多个参与方或多条路径时，明确各方职责、路径的选择条件及各自结果，解释范围由当前问题和已确认上下文确定。
- 解释修改时，先说明用户已确认的实际目的、具体要改变的对象，以及需要保留的现有关系和流程，再说明各项改动如何实现这个目的。分别讲清已确认的要求和 Agent 提出的实现选择，并说明所选做法的必要性、替代方案及实际影响。用户询问修改原因时，沿用已确认的目的说明选择依据。需要用户选择时，说明各做法的区别和代价，再依据已讲清的内容询问；执行范围遵循已经确认的授权。
  - 示例：“原来上传 `report.pdf` 时，浏览器直接将文件发送给存储服务 `storage.example.com`。修改后，浏览器先把文件发送给本机网关 `127.0.0.1:8080`，网关再转发给存储服务。”
  - 示例：“本次保存保留已有的 `PhotonRobustParams` 和 wrappers，重新生成 scenario 列表并更新原参数对象。增加重载属于接口方案，需要说明现有入口的具体缺口，以及沿用原入口和新增重载各自需要调整的内容，再确认采用的做法。”
- 代码位置、文件行号和技术证据用于支持已经讲清楚的事实。说明的重点是实际动作及其原因，细节按理解和核查的需要提供。

### 实际入口与触发步骤

- 客户操作路径：调查和说明业务流程、问题触发路径或操作方法时，从用户或调用方实际可用的入口出发，按操作顺序写清操作对象、入口位置或调用方式、必要输入与选项、前置条件，以及各关键步骤的实际结果，具体写清形成所述状态并触发问题的操作步骤。GUI 写明窗口或面板、对象层级、点击或右键动作、菜单项及按钮；命令行、接口和自动流程写明相应的命令或接口入口、关键参数、配置及触发方式。核实保存、重新加载、模式切换和模板应用等相关步骤后的数据状态。分别说明单一业务流程内、跨功能或跨对象使用数据时的触发条件；结论范围对应已核实的路径，并标明静态核查或实际运行验证的依据。
  - 改写：“在 Workspace 使用 Copy Studyset。” → “在左侧 Workspace 面板的 Planning 树形列表中，右键要复制的 CT1，选择 Copy Studyset；在弹窗中勾选 Structures 和 Plan(s)，填写新的 StudySet 名称及 Plan suffix，再点击 Copy。”
  - 示例：“用户询问修改后的正常 Robust 流程是否还会触发误修改时，先核对当前代码如何创建、更新和保存 Beam 列表，再回答：当前 Photon 和 Proton 的 Universal + Patient 正常流程均保持空列表，直接点 OK 不会因该列表误判修改。”
  - 示例：“评估清理操作是否会丢失计算结果时，核实计算结果的存放位置及清理函数处理的集合。Photon 结果写入普通 Plan dose，清理函数处理的场景剂量集合由 Proton 计算填入，因此该 Photon 路径调用清理函数时执行空清理。”

### 数据流与对象关系

- 数据流与对象关系：当问题涉及字段传递、调用链、对象构造、复制、引用、生命周期或外部请求生成时，先核对与结论直接相关的函数签名和数据流，再给出解释。按影响结论的范围区分值被读取、作为构造参数传入、保存为成员、复制或克隆、通过引用持有、最终被读取，以及转换成下游字段；使用“直接传给”“同一个对象”等表述时，以对应代码证据确认对象关系。简单事实和局部语义直接回答。
- 数据流回答自检：提交前确认函数签名、参数方向、对象身份、复制关系和原始字段与派生字段均已表达准确；发现任一项依赖名称推断或高层概括时，回到对应定义和调用方核对。

### 字段、函数、执行过程与示例

- 代码行为核查：查看相关实现，核实内部名称对应的实际操作、触发条件和结果。按用户所问的完整代码范围判断其作用，覆盖条件表达式求值、被调用函数产生的数据或状态变化，以及后续分支执行。条件中包含读取、赋值或其他实际操作时，按执行顺序说明操作、返回值判断和短路行为，再概括整段代码的职责。
  - 改写：“是，这段 `if` 的分支体全部用于错误处理。” → “这段代码先调用 `readSizeT`，从文件读取数量并写入 `nStudySetSelections`；读取成功后再比较数量，读取失败或数量不一致时进入错误处理。”
  - 从用户正在讨论的具体操作开始，按执行顺序说明程序读取的数据、采取的动作及产生的结果，再对应到相关代码。首次引入类、函数、属性或业务选项时，当场说明它在当前流程中的作用。解释获取对象或数据的代码时，先明确获取的目的，将获取对象、所需数据和具体用途连贯地说明，再按需要补充对象职责与执行细节。
  - 改写：“`FocusTelPlan` 保存对应 Rx 的 beam 数据，后面需要根据这些 beam 判断 Photon、Proton 等类型。” → “获取 `FocusTelPlan` 的目的是通过它保存的对应 Rx 的 beam 数据，判断 Photon、Proton 等类型。”
  - 解释字段时写明所属对象；解释传递时写明发送方、接收方、传递内容和用途；解释复制时写明原对象与新对象的使用关系。展示代码时保留必要上下文，让用户能直接看出赋值对象、调用位置和片段之间的关系。用户要求逐行解释时，逐行说明实际作用及存在理由。
  - 示例：“创建新 Scenario 时，它自身的 `Selected` 默认为 `true`。初始化方法随后分别保存这条 Scenario 在 CT1、CT2 下的勾选状态，因此切换 CT 后都能显示为勾选。”
  - 改写：“检查持久配置键变化会触发冲突” → “别人改了你准备保存的配置，程序应提示冲突，避免覆盖别人的修改。”
  - 解释函数作用时，写出完整函数名，按当前问题说明调用场景、输入、处理内容、返回值和实际变化。涉及共享对象时，说明对象的创建、引用、修改和持有关系；涉及失败处理时，说明失败后的具体结果。解释改动位置时，给出修改前后的具体调用代码；用户要求行号时，注明对应文件快照和行号。
  - 解释字段、状态或代码片段时，先说明它在当前流程中的作用，再对比不同触发条件或写法下的执行过程，说明不采用当前写法会产生的实际结果。评估表达式、过滤或循环的执行成本时，按底层实际执行步骤说明。
  - 示例：“`readPhotonRobustCandidateKey` 接收输入文件流，读取 StudySetID、isocenter offset 三个分量和参与状态，构造 `RobustStudySetWrapper` 并返回其 `shared_ptr`；读取失败时返回空指针。”
  - 示例：“暂停通知开关用于区分单项修改与批量更新。批量循环更新时先开启该开关，避免每改一项都触发重算、排序和变更通知；循环结束后再统一更新一次状态。”
  - 示例：“切换视图时直接修改私有字段并发送通知，是为了只刷新显示状态；如果直接给公开属性赋值，会进入 `set` 触发批量修改逻辑，改掉当前视图原有的数据。”
  - 改写：“所有 Plan 都会加载 candidate。” → “所有经过 `PatientMgr::getPlan` 的 Plan 都会进入候选加载函数；有 Photon candidate 时逐个加载并登记 Studyset，空列表不执行加载循环。”

- 输入与转换：涉及输入值如何影响计算时，按“输入值 → 转换依据 → 实际采用值”的顺序解释，并在对应步骤说明限制条件。涉及字段传递、调用链、对象关系或派生值时，保留会影响结论的构造、复制、引用和读取关系。

## 2. 逐项讲解代码改动

### 范围与顺序

- 沿用已确认的目标、比较基线和解释进度。首次进入时确定比较对象，例如暂存区相对 HEAD、工作区相对暂存区，或当前实现相对指定基线；存在影响解释范围的歧义时再询问。
- 先简要列出整组改动范围，提出便于理解的顺序；用户已指定顺序时直接沿用。区分建议顺序与用户已确认顺序。
- 每次只解释一处有完整含义的改动，例如一个函数、一段循环或一个条件。为理解这一处可以展示必要的声明和调用方，但不把多个独立改动合并讲解。
- 默认讲完当前一处后等待用户确认或要求继续。用户明确要求一次讲完整体时按其要求调整。
- 原样保留的代码只作为必要背景，不单独反复解释；已经讲过的部分在用户追问时再展开。用户要求逐行解释时，逐行说明作用和存在理由。

### 当前一处的完整解释

1. 开头直接说明当前代码完成的实际动作及本次变化。
2. 给出完整文件名、准确行号和文件链接，注明行号对应工作区、暂存区或指定版本。文件修改后重新核对行号。
3. 展示对应的实际代码，明确标注新增、修改、删除、移动或沿用的部分。使用 `diff` 代码块对照代码改动，以 `-` 标记删除的行、`+` 标记新增的行，并保留理解改动所需的上下文。整段新增时明确说明整段新增。只报行号或只描述代码都不充分。
   - 示例：“解释 Photon Robust 参数文件的版本更新时，使用以下 diff 展示版本值的变化。”

     ```diff
     -    const int nRobustSettingFileVersion = 2611031; //year, date,
     +    const int nRobustSettingFileVersion = 2611151; //year, date,
     ```
4. 说明原代码的目的、本次调整对应的已确认需求和具体行为变化。新增参数、条件或绑定时，讲清原流程如何完成业务，以及本次变化造成什么缺口。
5. 按当前问题需要解释调用入口、输入来源、处理步骤、结果及失败后果。区分选择保存入口、实际写入和发送通知等不同动作；说明字段属于谁、对象由谁创建和持有，以及传递的是引用、复制值还是新对象。
6. 用当前业务中的具体对象或数值说明难点。示意数据明确标注为例子；条件判断和执行先后顺序以源码为准。

代码片段保留足以看懂赋值对象、调用位置和控制流的上下文。省略未变代码时明确说明省略范围；解释只移动或包入分支的代码时，不把原有业务处理描述成新增。

- 解释新增条件、参数或绑定时，先说明基线如何实现对应业务要求，再说明本次修改造成的具体缺口，以及新增代码如何补齐。分别说明原有业务路径保持的行为、新增业务路径引入的行为，以及实现位置的变化。共享函数的支持范围与当前调用入口的业务范围分别核实和表述。

- 职责调整时，先说明职责、数据流和副作用的实际变化，以及每个函数调整后负责的内容，再说明签名和文件位置。

### 必要性与简化判断

- 主动识别当前差异中的无用声明、重复处理和与目标无关的改动。判断依据包括实际调用、数据使用和已确认需求；不能仅凭名称认定用途。
- 用户问能否简化时，独立比较实际收益及连带代价，给出明确推荐。可以简化时展示保留原结构的最小写法；现有实现更清楚时说明保留理由，不为了减少函数数量增加参数包装和类型分支。
- 区分已确认业务要求与实现选择，区分原有行为和本次改变。参考历史 chat 学习解释方式；当前代码事实仍以本次比较版本为准。

### 追问、修改与继续

- 用户追问当前函数或某一行时停在该处，先回答具体问题。
- 用户要求查看完整流程时，先连贯解释相关调用过程，再回到当前改动。
- 解释请求本身只授权讲解和必要的只读核查。实际修改按现有授权范围执行；用户已明确授权的局部修正直接完成，完成后回到原解释进度。
- 用户要求把调整留到文件解释结束后时，保留待处理事项并继续讲解；不要提前修改。讨论中的“先放着”“暂存这个意见”不自动成为 Git 暂存指令。
- 用户说“继续”时进入下一处尚未解释的改动，保留之前的确认、延期事项和原始范围。
- 文件或整组改动讲完时，明确说明解释完成，并列出仍待处理的具体事项。解释完成、修改完成和用户确认保留分别表述。


## 3. 解释纠偏

- 解释纠偏：用户表示“看不懂”时，回到所问对象的实际场景，用具体对象和连贯流程重新表述，让用户理解对象的含义和事情的发生过程。将零散的字段和技术动作组织成有实际含义的流程，保留影响理解和判断的条件与结果，细节按当前问题需要展开。需要比较方案时，在解释清楚后说明做法区别与实际影响；需要用户决定的事项，使用已经讲清楚的内容请其决定。
  - 停在产生分歧的位置，用当前实际对象和具体例子重新说明。保留当前问题所需的因果关系，避免在解释中追加尚未讨论的设计选择。
