# Debug

从当前版本的真实业务操作出发，查明触发前提、共性根因和实际后果，在已确认范围内完成最小修复。

## 目标、阶段与授权

- 结合上下文确认用户正在问的对象、版本、状态、操作范围，以及预期行为、实际差异和验收条件。
- 区分业务要求、已确认约束和待核实假设。沿用已有事实与授权；只针对会改变结果、范围或风险的缺口提问。
- 先解释调查结论与修复方案，按用户明确授权实施。用户要求先调查、先审方案或逐步确认时，在相应阶段交付并等待确认。
- 工具选择、代码事实调查的分工、写入和验证权限遵循适用的 AGENTS.md 与专项规则。主 Agent 负责根因判断、方案比较、修改范围和最终结论。

## 沿真实操作调查

- 从用户能够使用的入口追踪完整操作链。GUI 核实窗口、可见控件、按钮启用条件和实际操作顺序；其他入口核实调用方式、权限和前置校验。
- 将每一步操作对应到实际调用、输入和状态变化，确认中间数据能够到达后续步骤。核对界面选择、内存数据、保存内容及重新加载后的状态。
- 涉及构造、复制、引用或生命周期时，核对函数签名、数据来源、对象身份、所有者及最终读取位置。
- 搜索相关调用方和共享实现，覆盖决定当前结论的正常路径、失败路径和数据传递边界。证据足以回答时停止搜索；已有材料足够时直接复用。

## 证明触发条件与实际影响

- 在提出修复方案前，先确认业务设计上有没有必要调整：核实相关功能、对象和关联的实际用途、应保留的业务关系及预期结果，据此判断当前行为是否需要修改。业务设计尚未明确时，说明影响判断的具体缺口并向用户确认。
- 先核实该问题在业务的正常流程中会不会触发：从用户实际操作入口追踪输入和状态变化，查明触发前提能否形成、具体操作步骤及实际后果，再据此确定需要处理的问题和范围。
- 评估后果时，核实问题发生当时受影响的数据或资源是否存在、是否已在此前操作中更新或清理，以及本次实际改变了什么。
- 区分真实业务变化与误判变化、当前流程生成的状态与其他来源带入的状态。分别说明单一流程内、跨功能或跨对象传递数据时的触发条件。
- 用户问“现在还会不会发生”时，先回答所指版本和流程中的结论与依据。将其他版本、历史状态或假设输入的分析明确限定到对应范围。
- 为关键结论提供源码位置、日志、配置或运行记录。区分已核实事实、条件推演和证据缺口，分别表述静态路径核查与实际复现结果。

## 解释根因与选择方案

- 用业务语言说明完整的触发经过：用户或调用方从哪个入口，对什么对象，按什么顺序执行哪些操作，使用什么关键输入或选项；程序在哪一步形成触发条件、发生什么错误，最终产生什么实际后果。操作描述具体到读者能按说明找到入口并理解触发过程。结合调查结果，明确回答该问题在正常业务流程中是否会触发，以及成立的必要条件。
- 有参考实现时，按相同业务条件比较操作覆盖、状态变化、数据流和失败处理，确认需要对齐的行为及应保留的差异。
- 提出覆盖已确认根因和相关调用路径的最小方案，说明改动位置、必要性、预期行为、影响范围和验证方式。
- 优先删除无用逻辑、复用现有能力，在职责和所有权合适的共享位置处理问题。新增检查、状态、接口、抽象或兼容处理须对应当前已确认要求或具体正确性问题。
- 将相邻问题和额外场景作为独立事项确认。出现纠正或新事实时，重新核对受影响的前提与整体方案，再按更新后的授权推进。

## 实施、验证与交付

- 一次处理一个明确问题，保护已有改动，保持局部风格及既有业务契约。
- 修改后核对相关声明、定义、调用方、数据流、状态写入点和差异，确认正常行为与失败处理符合已确认目标。
- 默认采用静态检查。新增测试、编译、构建、运行测试和实际 GUI 操作，按适用规则及用户授权执行。
- 交付时先报告实际完成情况，再说明修复覆盖的业务路径、验证证据和仍待验证的部分。结论限定在已检查的对象与流程内。
