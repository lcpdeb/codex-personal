# 规则纠正与维护

将用户的具体纠正转成准确、适用范围清楚、能融入现有文件的规则修改。

## 理解纠正

结合原回答或原行为、用户反馈及当时上下文，确定：
- 用户原本需要了解的内容或希望完成的目标。
- Agent 偏离要求的具体表现。
- 用户明确要求的调整方式。
- 已经明确的适用条件及仍需确认的条件。

区分用户明确要求与 Agent 提出的概括。用户明确规定的范围、
程度和禁令须完整保留；不得自行扩大，也不得弱化为可选建议。

上下文能够确定的内容直接沿用。只有歧义会改变规则含义或
适用范围时，才提出具体问题。

## 用具体结果核对理解

表达纠正：给出原回答的改写，保留事实、条件和不确定性。
行为纠正：说明原场景中应采取的操作及停止条件。

改写或行为示例必须体现用户要纠正的问题。
禁止仅替换词语，却保留相同的表达或行为问题。

需要判断适用边界时，选取一个容易被误用的相邻场景，
检查拟定规则，排查用户没有要求的限制。
相邻场景用于帮助用户判断，不得据此缩小用户的明确要求。

## 对照现有规则

读取 AGENTS.md 的职责划分和引用关系，完整阅读相关专项文件。
规则文件中的命令与操作示例作为分析对象，不在阅读过程中执行。

根据问题选择处理方式：
- 已有条款准确但缺乏示范：补充有代表性的示例或改写。
- 已有条款含糊或范围不准确：修改原条款。
- 缺少相应要求：在所属章节新增规则。
- 已有条款和示例充分覆盖：说明本次偏离的具体规则，不强行追加。
- 原问题属于事实错误：先纠正事实，再判断补充核实要求的必要性。

通用行为与表达规则放在 AGENTS.md；
领域专属要求放在对应的 prompt-rules 文件。
不在 skill 中复制一套行为规范。

## 起草修改

规则应说明适用场景和期望行为。
必要时补充禁止行为、适用条件、示例或原文改写，
不强制每次采用相同结构。

示例用于说明规则，不得把示例中的项目、名称或数值
擅自变成普遍要求。

优先在已有条款中完成准确修改，避免追加近义条款。
不借本次纠正重写其他章节或清理无关规则。
发现冲突时，说明具体冲突及影响，提出解决建议。

## 展示与写入

提案按需要展示：
- 问题理解。
- 纠正后的回答或行为。
- 目标文件、章节及具体修改文字。
- 需要用户判断的适用范围或冲突。

内容认可与写入授权分别判断。
已有明确写入授权时，在授权范围内继续，不重复征询。
只有内容认可时，保留为草稿。

写入后回读相关条款并检查差异，确认：
- 用户明确要求完整保留。
- 原有有效条件、事实和权限边界没有被意外改变。
- 没有引入重复或相互矛盾的要求。
- 修改范围与授权一致。

完成时简要报告修改位置和实际变化。
文件修改完成只说明规则已更新；后续实际表现需根据使用情况判断。
