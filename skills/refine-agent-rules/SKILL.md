# 规则纠正与维护

理解用户纠正的实际问题，将其提炼为清晰、可复用的要求，并更新到职责对应的规则文件。

## 整体表达要求

**所有内容只突出要做什么。**

分析、建议、规则正文、改写和示例，都围绕当前问题直接说明相关对象、应采取的行为和预期结果。

说明完成情况时，**只说实际做了什么**。

## 理解用户的纠正

结合原回答或操作、用户反馈和上下文，确认：

- 用户希望达到的目的。
- 原回答或操作中需要调整的具体内容。
- 用户明确提出的要求。
- 本次纠正体现的可复用原则。

区分用户明确要求与 Agent 自己的概括，以用户明确要求确定规则的含义、范围和强度。

上下文已经明确的内容直接沿用。存在会改变规则含义的具体分歧时，说明分歧并向用户确认。

## 提炼规则的范围与重点

**适用范围默认通用。** 用户未明确限定适用范围时，提炼出的规则默认适用于所有项目、任务和回答；用户明确限定范围时，按其指定范围处理。

规则正文表达可复用的要求，具体事件用于说明该要求在实际场景中的应用。

优先采用用户已经给出的准确表述，保留其明确要求的关键词、强调方式和要求强度。

## 检查现有规则

先读取 AGENTS.md，了解相关条款、文件职责和引用关系，再完整阅读本次纠正涉及的专项规则。

将用户纠正与现有条款、改写和示例逐项对照，判断问题出在：

- 规则的含义或适用范围。
- 规则对预期行为的说明。
- 示例对实际场景的展示。
- Agent 对已有规则的执行。

以文件原文和实际交互为依据，说明具体问题及其影响。涉及事实错误时，先核实并纠正事实，再判断规则需要怎样调整。

## 判断修改方式

**由 Agent 根据实际问题和现有规则，判断是否需要调整，以及采用哪种调整方式。**

- 现有条款含义或范围需要调整时，修改对应条款。
- 用户要求需要新的规则承载时，在职责对应的章节补充条款。
- 具体表达或行为需要示范时，补充改写或示例。
- 现有条款和示例已经充分覆盖时，说明对应要求及本次应如何执行。

说明所选方式解决的具体问题。按实际需要组合条款、改写和示例，以清楚传达用户要求为标准。

通用行为和表达要求写入 AGENTS.md；领域专属要求写入对应的专项规则。skill 负责指导规则维护的判断与执行流程。

## 起草修改内容

优先在承载相同要求的现有条款中完成调整，修改范围围绕本次纠正确定。

规则正文直接说明应采取的行为，以及影响其含义的必要条件。

需要改写时，使用：

改写：“原文” → “改写后的回答”

改写保留影响当前问题含义和判断的事实、条件及不确定事项，展示用户要求如何落实到实际表达。

需要示例时，选用能够直接说明规则的具体场景，写清相关对象、实际行为和结果。示例的详略以理解规则所需的信息为准。

模板格式：

- 示例：“文件上传服务仍使用启动时从 `config.json` 读取的上传大小上限 10 MB；重启后会读取文件中修改后的 20 MB 上限。”
- 改写：“上传大小上限没有更新。” → “文件上传服务仍使用启动时从 `config.json` 读取的上传大小上限 10 MB；重启后会读取文件中修改后的 20 MB 上限。”

示例和改写必须分别严格遵循上述模板；展示草案前和写入后回读时，逐项核对格式。

发现规则冲突时，说明冲突条款、实际影响及建议采用的处理方式。

## 展示草案与确认

展示前，将草案与用户的纠正逐项核对，确认：

- 适用范围符合用户要求或默认通用范围。
- 要求强度和关键含义准确。
- 用户指定的关键词和强调方式得到保留。
- 所选条款、改写或示例能够解决实际问题。
- 各部分只突出相关对象、应采取的行为和预期结果。

用户对草案提出局部修改时，将修改合并进完整草案；再次展示时，一并呈现草案中已有的规则、示例和改写，沿用上下文已经明确的内容。

向用户展示问题判断、修改依据、目标文件、修改位置和具体草案，然后等待确认。

用户针对已展示草案明确授权写入后，按确认内容执行。已有明确写入授权时，继续完成对应修改。

## 写入与完成

写入后回读相关内容并检查差异，核对：

- 写入内容与已确认草案一致。
- 用户明确要求完整保留。
- 相关条款之间含义协调。
- 有效事实、必要条件和权限边界保持准确。
- 实际修改范围符合授权。

完成后简要说明修改位置和实际更新内容。
