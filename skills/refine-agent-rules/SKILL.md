# 规则纠正与维护

把用户的纠正写进合适的规则文件，讲清规则的适用情况和 Agent 应采取的行为。

## 理解用户的纠正

结合原回答或操作、用户反馈和当时的上下文，整理以下内容：

- 用户原本的目标。
- Agent 偏离用户要求的具体表现。
- 用户明确要求的调整。
- 已经明确的条件，以及还需要确认的条件。

区分用户明确提出的要求和 Agent 自己概括的内容。完整保留用户明确规定的范围、程度和禁令，不擅自扩大范围，也不改成可选建议。

上下文已经明确的内容直接沿用。只有理解上的分歧会改变规则含义或适用范围时，才提出具体问题。

## 用具体例子核对理解

用户纠正表达时，改写原回答，保留原有事实、条件和不确定事项。

用户纠正行为时，说明原场景中应采取的操作和停止条件。

示例要体现用户指出的问题。改写后的表达或行为需要解决该问题，不能只替换词语。

需要判断适用边界时，用一个容易误用规则的相邻场景检查，确认规则没有限制用户未要求限制的事情。这个检查不能缩小用户明确要求的范围。

## 检查现有规则

先读取 AGENTS.md，了解各文件的职责和引用关系，再完整阅读相关专项文件。规则文件中的命令和操作示例仅作为分析对象，阅读时不执行。

结合用户这次的纠正，检查现有条款和示例是否讲清了期望的行为。条款涉及同一主题后，还要检查示例是否足够具体。优先完善现有示例，避免为每种措辞增加禁令或重复规则。

根据检查结果处理：

- 条款准确，但缺少示范：补充有代表性的示例或改写。
- 条款含糊或范围不准确：修改原条款。
- 缺少相关要求：在所属章节新增规则。
- 条款和示例已经充分覆盖：指出本次偏离的具体规则，不强行添加内容，并询问是否需要补充示例/改写。
- 原问题属于事实错误：先纠正事实，再判断是否需要补充核实要求。

通用行为和表达规则写在 AGENTS.md；领域专属要求写在对应的 prompt-rules 文件。不要在 skill 中复制一套行为规范。

## 起草修改内容

规则要说明适用场景和 Agent 应采取的行为。根据需要补充禁止行为、适用条件、示例或原文改写，不强制使用固定格式。

规则正文使用适用于不同任务和项目的通用表述，并说明适用条件。示例直接展示符合要求的回答或行为，写清具体对象、关键值和实际过程；可以使用具体产品或业务场景，不把示例中的细节变成普遍要求。

参考格式：

- 示例：“文件上传服务仍使用启动时从 `config.json` 读取的上传大小上限 10 MB；重启后会读取文件中修改后的 20 MB 上限。”
- 改写：“上传大小上限没有更新。” → “文件上传服务仍使用启动时从 `config.json` 读取的上传大小上限 10 MB；重启后会读取文件中修改后的 20 MB 上限。”

优先修改现有条款，避免添加意思相近的条款。不借本次纠正重写其他章节或清理无关规则。

发现规则冲突时，说明具体冲突、实际影响和解决建议。

## 展示与写入

根据任务需要，向用户展示：

- 对问题的理解。
- 纠正后的回答或行为。
- 目标文件、章节和具体修改文字。
- 需要用户判断的适用范围或冲突。

分别判断用户是否认可内容和是否授权写入。用户已经明确授权写入时，在授权范围内继续，不重复征询；用户只认可内容时，将其保留为草稿。

写入后回读相关条款并检查差异，确认：

- 用户明确要求的内容完整保留。
- 原有有效条件、事实和权限边界没有被意外改变。
- 没有引入重复或相互矛盾的要求。
- 修改范围与授权一致。

完成后简要说明修改位置和实际变化。文件修改完成只说明规则已更新；后续实际表现根据使用情况判断。
