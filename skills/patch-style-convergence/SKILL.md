# 补丁风格收敛

在保护已确认基线和权责边界的前提下，将当前责任范围内的实现收敛为整体理解成本最低、最符合当前仓库惯用方式的改动。

## 执行

1. 先使用 `baseline-attribution`，请用户明确确认本次权威基线；确认前不读取仓库或比较代码。
2. 基线确认后，读取适用的 `AGENTS.md`、专项规则、基线完整快照、当前差异、受影响文件和邻近同类实现，区分基线范围与当前改动引入、扩大或恶化的范围。
3. 明确补丁必须保持的输入、输出、副作用、失败语义、所有权和生命周期；缺少会改变这些内容的决定时停止并询问用户。
4. 在当前责任范围内比较候选实现，以职责清晰、数据流直接、状态唯一、接口语义准确、生命周期闭合和隐含规则最少为主要标准。代码行数、文件数量和差异大小只作为次要参考。
5. 搜索拟修改符号的全部调用方，优先删除无用代码、复用现有实现和标准能力；需要重构或调整接口时，以降低整体理解成本和保持权责清晰为依据。
6. 默认只修改当前改动负责的代码，使其适配基线已有的设计、共享接口和功能。不得为了局部方便，将当前责任转移给基线代码或扩大共享契约。
7. 修改基线设计、共享接口、范围外代码或已确定功能前，说明必要性、影响范围、全部调用方、替代方案和验证方式，并取得用户对本次跨边界修改的明确授权。
8. 完成已授权范围内最合适的补丁，并静态检查差异、声明与定义、调用方和引用关系。构建与测试仅在用户明确授权后执行。

## 边界

- “当前责任范围”指当前改动引入、扩大或恶化的代码和行为；基线既有且未受当前改动影响的内容保持不动。
- 最小实现以整体理解成本为准。更大的局部重构可以是更合适的实现，但跨越基线或权责边界仍须用户明确授权。
- 不为未来需求新增抽象、配置、依赖、重载、兼容层或测试脚手架。
- 不把个人偏好覆盖到已有仓库规则之上；仓库规则和稳定的邻近模式是风格事实源。
- 不借收敛之名修复范围外缺陷；发现后单独报告。
- 交付时列出实际修改、静态证据和未验证行为。
