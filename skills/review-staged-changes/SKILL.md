# 暂存区代码改动严格审阅

## 手动调用边界

仅在用户明确调用 `$review-staged-changes` 或明确要求使用本技能时执行。仅提及技能名称、讨论或修改技能说明不构成调用。

“审查暂存区”“pre-commit review”等普通任务表述，以及“暂存改动能否解决某个风险”等定点问题，均不自动启用本技能；按用户实际问题处理，不因此连带启用 `baseline-attribution`。其他工作流也不得代替用户自动调用本技能。

以下审阅流程及基线前置要求只在满足上述手动调用条件后适用。

只读审阅当前 Git 暂存区（staged）的代码改动。先明确这次改动要解决的问题，在不看暂存区具体实现的前提下独立形成方案，再阅读代码、对比方案，按已明确的意图验证实现：

- **行为保持型**（重构、性能优化、清理、格式调整）：验证实现目的、业务逻辑、输入输出语义和外部可观察行为完全不变。
- **缺陷修正**：验证缺陷本体判断准确、根因位置选择正确、同类路径一并覆盖，且修正未把影响外溢到缺陷范围之外。
- **功能改进**：验证新行为自洽、既有调用方受到的影响已被识别、新增状态与资源的生命周期完整。
- **混合**：同一批改动同时包含以上多种意图，逐项拆解后分别判定，并评估是否应拆分提交。

审阅结论评价**实现与意图的相符程度**，不评价**行为有无变化**。缺陷修正与功能改进本就应当改变行为，这类改动不因行为变化本身而降级。

## 执行约束

- **只允许**读取代码、运行只读 Git 命令和纯文本搜索。
- **不允许**自动修改代码、自动提交、格式化文件。
- **不允许**执行可能改变工作区、数据库、网络状态或外部服务状态的命令。
- **不允许**编译或构建，也不允许运行任何依赖构建产物的工具。
- **不允许**运行测试。

## 审核阶段的仓库状态

本技能运行在业务代码审核阶段。该阶段的仓库处于以下状态，判定时必须据此取舍事实源：

1. **测试代码滞后，不作为判定依据。** 测试在业务代码审核通过之后才补写，因此暂存区中的业务改动通常没有对应测试，现存测试也可能仍在描述改动前的旧行为。不要阅读测试代码来推断业务意图，不要用"现有测试会失败"作为反对改动的理由，也不要用"现有测试仍然通过"作为改动安全的证据。若暂存区本身包含测试文件改动，照常分类审阅，但仍不得用它反推业务代码的正确性。

2. **文档滞后，不作为判定依据。** 文档同样在审核通过之后才更新，因此仓库内的设计文档、wiki、README 可能仍在描述改动前的模型。文档与代码冲突时以代码为准，不要因为文档未同步就判定改动有风险。文档缺口不进入风险点。

3. **不编译、不运行。** 审核只做静态语义比较，不通过编译或运行来验证。因此不得把"编译通过"或"测试通过"列为验证证据；遇到必须构建才能确认的问题，直接在风险点里写明"需人工构建验证"。

4. **目标构建为 Release，不考虑 Debug 构建。** 交付和运行的都是 Release 构建（包括 `RelWithDebInfo` 等定义了 `NDEBUG` 的配置），Debug 构建仅用于本地排查。由此产生两条方向相反的要求，都必须执行：

   - Debug 专有路径（`#ifdef _DEBUG` 分支、`assert`、调试期同步、调试日志）在 Release 下不存在，它们带来的性能开销、额外副作用和行为差异**一律不列为风险**，也不必比较其改动前后的调用次数或耗时变化。
   - Release 下这些机制全部失效，因此**依赖** Debug 专有机制来保证正确性的代码**一律判为风险**。典型例子是用 `assert` 校验生产环境必须成立的不变量：它在目标构建中被编译掉，等同于没有检查。此类情况应建议改为在 Release 下同样生效的检查（显式判断并抛出或返回错误）。

   判断某个宏、断言或分支在目标构建下是否生效时，以构建配置为准（例如 CMake 中对 `NDEBUG` 的定义），不要凭命名假设。

问题目标与验收标准以用户明确说明为准；代码用于核实现状与实现效果，不得用暂存区实现反推或替换目标。实现事实的判定依据优先级：业务代码本身 > 接口契约与注释 > 构建配置 > 文档 > 测试。

## 基线归属前置检查

默认以 `HEAD` 完整快照为基线、Git index 为当前审阅对象；用户明确指定其他基线时按用户指定。未暂存工作树不属于任一比较对象。前两步只读取问题说明、改动文件清单和基线代码；完成独立方案后，在第三步开始实现审阅时必须先使用 `baseline-attribution` Skill，不能因归属检查提前读取暂存区实现。

对每个候选风险只检查完成归属判断所需的最小基线范围，并归入以下一类：

- **当前新增**：基线不存在，暂存改动引入。
- **当前扩大**：基线已有问题，暂存改动增加了受影响的输入、调用方、对象或数据范围。
- **当前恶化**：基线已有问题，暂存改动提高了发生频率、严重程度、副作用或恢复代价。
- **基线未变**：基线已有，暂存改动没有改变其触发条件或影响。

最终 findings 只保留当前新增、当前扩大和当前恶化。基线未变的问题立即排除，不继续调查、不提出修复，也不写入风险点、总体结论或建议。若基线缺失或不唯一且会改变归属结论，先询问用户并停止审阅；归属证据充分时由 Agent 直接下结论，不能要求用户代为定性。

## 审阅流程

### 第一步：明确这次改动要解决的问题

先只读取改动文件清单以定位范围，不读取 diff 内容或 index 中的文件正文：

```shell
git diff --staged --name-only
```

如果暂存区为空，告知用户并终止。

结合用户的问题说明和基线业务代码，明确实际问题、当前行为、预期结果、约束与不应改变的范围，并标明事实来源。读取基线文件使用 `git show HEAD:<path>`；指定其他基线时替换 `HEAD`，不要用工作树文件代替基线。

问题目标或验收标准不明确且会改变审查结论时，先询问用户并暂停；不得通过偷看暂存区实现来补齐需求，也不得把自己的推断当作已确认目标。已有说明充分时直接继续。

### 第二步：不看暂存区实现，独立形成方案

只根据第一步的问题与基线现有代码，检查相关数据流、共享实现及调用方，提出满足目标的最小方案：改在哪里、复用什么、关键行为与边界如何处理，以及用哪些代表性正反例静态检查预期效果。不编写补丁，也不扩展到无关问题。

在阅读暂存区实现前，先向用户简要记录问题理解、独立方案、关键依据与待验证项，作为后续对照。若当前上下文已经包含暂存区实现，明确披露独立性受限，不得声称方案是在未看实现的情况下形成。

### 第三步：读取暂存区实现并分类

完成前两步后，使用 `baseline-attribution`，再读取暂存区 diff：

```shell
git diff --staged
```

如果 diff 过大，按文件逐个查看；需要完整实现与调用链时读取 index 快照（如 `git show :<path>`）：

```shell
git diff --staged --stat
git diff --staged -- <file>
```

按第一步明确的问题判定整批改动的意图，再用代码核对实现效果；commit message 和实现本身均不能替代已明确的问题目标：

| 意图 | 判定特征 | 对应验证标准 |
|------|---------|------------|
| 行为保持 | 执行路径、数据流、副作用在所有输入下均与改动前等价 | 语义等价性 |
| 缺陷修正 | 改动前存在可触发的错误行为，改动后该行为消失 | 根因覆盖度与影响边界 |
| 功能改进 | 新增能力或有意改变既有行为，改动前的行为并非缺陷 | 新行为自洽性与调用方影响 |
| 混合 | 同一批改动同时命中以上多项 | 逐项拆解后分别判定 |

再按文件分类，每个改动归入以下类别之一：

| 类别 | 含义 |
|------|------|
| 纯格式/注释 | 空白、注释、格式化 |
| 重构 | 提取/合并/拆分函数、重命名 |
| 性能优化 | 算法改进、减少计算量 |
| 逻辑调整 | 分支、条件、数据流变化 |
| 测试改动 | 测试用例的增删改 |
| 配置改动 | 配置文件、环境变量 |
| 依赖改动 | 包管理、依赖版本 |
| 其他 | 不属于以上类别 |

### 第四步：逐段比较改动前后的语义

不要只看代码表面像不像优化。必须判断执行路径、数据流、控制流与副作用的实际差异。

逐项比较改动前后：

1. **输入参数的处理方式**
2. **返回值**（类型、语义、大小、顺序）
3. **异常的抛出、捕获、吞没与错误码**
4. **分支条件**
5. **循环边界**
6. **默认值**
7. **空值、边界值与异常值的处理**
8. **状态修改顺序**
9. **IO、网络请求、数据库操作与其他副作用**
10. **并发、异步、锁、回调与对象生命周期**
11. **配置项、环境变量、路径、文件名与序列化字段**
12. **对外 API、CLI 参数、日志格式与协议格式**
13. **资源生命周期与所有权**（分配与释放时机、共享范围、越界或失效后的后果）
14. **Release 构建下校验与断言的实际效力**（`assert` 与 `#ifdef _DEBUG` 保护的检查在目标构建中已被编译掉，不能用来保证生产环境的不变量）

对行为保持型意图，任一项存在差异即为问题。对缺陷修正与功能改进，差异本身是预期的，判定重点转为：该项差异是否落在意图声明的范围内，以及范围之外的项是否确实无差异。

### 第五步：对比独立方案并给出结论

将暂存区实现与第二步记录的独立方案对照，比较目标覆盖、根因与同类路径、边界及调用方影响、复杂度和维护成本。以代码证据说明实际实现的优势、遗漏和取舍；若新事实使独立方案不成立，明确修正原因，保留原方案与修正的区别。

独立方案只是对照，不是标准答案。实现不同、命名不同或个人风格偏好均不构成风险；只有有证据支持且通过基线归属检查的当前新增、扩大或恶化问题进入 findings。对照发现的基线未变问题仍按前述规则排除。

结论只能使用以下四类之一：

| 结论 | 含义 |
|------|------|
| **PASS** | 实现与识别到的意图相符，未发现意图之外的行为变化 |
| **PASS_WITH_ASSUMPTIONS** | 实现与意图相符，但结论依赖若干未经验证的假设，假设已逐条列出 |
| **RISKY** | 存在产生意图之外行为的合理路径，需人工确认或补充验证 |
| **FAIL** | 实现与意图不符：行为保持型改动改变了行为、缺陷修正未覆盖根因或外溢到无关路径、功能改进破坏了既有调用方、或多种意图混在同一提交内且未拆分 |

## 审阅规则

1. 不要因为代码看起来更简洁就默认安全。
2. 行为保持型改动里夹带的逻辑变化必须单独指出并要求拆分。缺陷修正与功能改进的行为变化本身不是问题，问题在于变化超出了意图声明的范围。
3. 不要只总结 diff，要判断语义等价性。
4. 不要建议无关重构。
5. 不要审阅未暂存代码。
6. 不要用测试或文档的现状反推业务代码的正确性，两者在审核阶段都可能滞后于代码。
7. 如果信息不足，必须明确说不能完全确认，而不是强行 PASS。
8. 对风险判断要保守。只要存在产生意图之外行为的合理路径，就至少判为 RISKY。
9. 如果改动涉及安全、权限、鉴权、计费、数据删除、远程调用、并发或持久化，默认提高一个风险等级。
10. 如果改动删除了代码，即使看似无用，也必须检查是否存在隐式副作用。
11. 只在 Debug 构建下才存在的行为差异，不构成把改动判为 RISKY 的理由，也不写进风险点；反之，把生产环境的不变量交给 `assert` 或 `#ifdef _DEBUG` 保护的检查来保证，属于必须报告的风险。详见"审核阶段的仓库状态"第 4 条。
12. 完成适用于本次改动的语义检查，报告影响结论的结果及覆盖限制；多个维度共用证据时可以合并说明。
13. 表格只是显示方式，不是长度约束。"依据"列以说清楚为准：需要多条推理就写多条，需要列出调用链就完整列出，不得为了排版整齐而压缩成结论式短语，也不得把本应在此说明的内容推迟到其他章节。同时不写"未发现问题"这类没有具体来源的空泛描述。
14. 依据和建议完整保留影响判断的证据、因果关系和必要条件，篇幅与结构以读者能够核对结论为准。
15. 引用代码位置统一使用 `文件名:行号` 形式，只用文件名不写仓库路径（如 `PlanOptimizationImplementationPgd.cu:1038`）。同一处涉及多个行号时并列写出（如 `PlanOptimizationImplementationPgd.cu:1038、:1048`）。
16. 单条风险的风险等级独立判定，不必与"改动概览"中所在文件的等级一致：文件等级取其中最高风险，单条风险按自身影响判定。
17. 审阅缺陷修正时，必须区分复现实例与问题本体：确认根因位置是覆盖同类问题的最小位置，检查共享实现路径上的其他调用方是否存在同一缺陷而未被一并修正，并确认修正没有把影响扩散到缺陷范围之外的路径。
18. 审阅功能改进时，必须列出既有调用方受到的影响：新行为对现有调用点的兼容性、新增状态与资源的完整生命周期、以及旧行为被依赖时的迁移代价。
19. 标题与条目使用陈述式表达，写明事物是什么、产生什么结果，不使用"是否……"的设问句式。
20. 每个风险点必须先完成基线归属；当前新增、当前扩大和当前恶化进入 findings，基线未变的问题不得进入任何结论。
21. 当前改动扩大或恶化基线问题时，只调查和报告当前增量，不把未受影响的基线缺陷扩展为本次审阅范围。
