# CODE：代码任务专项规则

本规则适用于代码、配置、Schema、构建脚本和代码审查，由上级 `../AGENTS.md` 按任务范围加载。

通用任务契约、事实依据、授权边界、解释与决策顺序，以及可读性原则，统一遵循上级 `../AGENTS.md`。本文件的写法、排版和表达形式条款是默认偏好；安全、契约、数据与所有权、授权和验证边界不因章节归类而放宽。

## 默认阶段性代码改动

本节的阶段性约定用于限定代码实施、完善和正式保留的范围。调查是否完成、何时给出最终结论，遵循 AGENTS.md 的“调查完成与最终结论”规则；即使本轮代码只是临时尝试，也须完成当前问题所需且已获授权的调查与复核。

项目改动默认是临时、阶段性的尝试。每轮只实现用户当前确认的一小步，再根据实际试用结果，由用户决定保留沿用、继续调整或换个思路。用户明确要求保留沿用之前，代码保持暂定状态，完成范围限定为当前阶段。

当前阶段只加入实现这一目标所必需的代码。面向未来的防御性处理、兼容、抽象、配置、额外日志、文档和其他完善工作，留到实际结果表明确有需要时，再说明依据、范围和影响，征询用户意见。已有安全措施、数据完整性保护和已确认业务约束继续遵守。

用户确认保留沿用后，再根据已经发现的实际问题提出必要完善项；确认保留本身不自动授权扩大修改范围。

临时尝试不代表授权新增测试代码，也不改变编译、构建、测试和 Computer Use 的执行权限。已确认的范围和权限继续有效，无需重复征询。收敛已有补丁时，保留符合当前目标的部分，只撤回或调整超出范围的部分。

## 调查与方案选择

- **改动追溯**：写入前，逐项确认每个拟修改文件和符号直接对应用户已确认的验收条件，并符合已核实的现有契约；拟增加的分支、变量和检查须对应已确认要求，或本次改动引入的具体正确性问题。发现边界情况时，先核实它与当前改动的关系、触发条件和实际影响。无法直接追溯的相邻问题及既有边界问题只报告，作为独立事项取得确认后处理；扩展项不得替代最小方案或与之打包确认。

- **最小修改与补丁卫生**：在职责、所有权和数据生效范围匹配的前提下，优先复用现有能力，只修改解决当前问题所需的最少代码，将调用、数据和接口变化限定在当前验收条件内，保留仍符合职责边界的现有结构、命名和实现方式。保护用户已有修改，避免无关格式化、预测性脚手架、空实现、占位分支和未来扩展点。

- **新增结构前**：新增成员、类型、函数或文件，仅在最小改动无法实现或验证已确认验收条件时提出，并逐项说明现有入口或状态的具体缺口。提出逻辑迁移、函数拆分或公共接口调整时，说明原职责位置无法满足当前需求或契约的具体原因，并将连带影响纳入方案比较。评估新增状态时，核对现有状态的使用顺序、可变性和生命周期；适合顺序复用的状态可以清空后复用，需要同时保留不同值的状态说明其独立存在的业务依据。

- **已触及冗余的收敛门槛**：已确认修改直接触及某项状态、所有权或数据流，并确认现有成员、别名、缓存或容器只是同一事实源的重复表示时，只有删除该冗余是实现当前阶段目标的必要条件，或用户明确授权该项收敛，才将其纳入本轮修改；其他冗余作为独立事项说明。纳入修改后，全部调用方改为读取唯一事实源，避免继续维护两个可表达同一状态的入口。删除会改变公共契约、兼容行为或生命周期，或者冗余与本次数据流无关时，仍需按边界规则单独确认。
  - 正例：用户已明确授权此项冗余收敛，且对象已通过 `models.at(0)` 唯一持有 Reference Model，本次修改又直接涉及该引用；确认额外的 `m_pReferenceModel` 没有独立赋值、所有权或生命周期作用后，删除成员并让调用方通过不保存状态的 accessor 读取 `models.at(0)`。

- **修改前调查**：先确认业务目标、核心不变量、验收标准和失败语义，再阅读受影响代码、配置、数据和项目契约，搜索全部调用方及项目内同类实现，核对完整调用关系、数据流和失败路径。如有 `openwiki/` 文件夹，强烈建议先阅读 `openwiki/quickstart.md` 及其相关链接，了解仓库设计和业务目的。在选择实现位置、接口、抽象、复用方式、数据结构或修改范围前，必须确定业务职责、状态和生命周期的所有者，后续设计和实现服从这些归属。

- **契约冲突**：用户明确要求和现有契约优先于通用最佳实践。二者冲突时，用户已知影响并明确授权修改契约的，服从用户要求；否则说明冲突和影响并等待确认。

- **假设隔离与级联阻断**：沿用 AGENTS.md 的假设边界；代码任务中的结构性变化包括新增或调整业务职责、状态或生命周期所有者、容器或数据结构、函数、类型、接口、参数、控制分支或文件范围。未确认假设只允许触发只读调查或提问；一个推断只要会引出第二项结构性修改，立即停止级联，列出假设、证据缺口和影响并等待确认。

- **最小实现的判断标准**：在满足正确性和已确认契约后，优先比较受影响的业务范围、模块耦合、状态与恢复责任、兼容性、验证成本和整体理解成本；随后比较代码量与文件数量。方案产生的连带修改计入总成本。新增影响超出已确认范围时，先说明必要性、影响及替代方案，再取得扩展授权。数据结构、类型、变量名和控制流直接表达核心业务含义与对象关系；为准确表达这些关系所需的类型和辅助逻辑计入方案的合理成本。
  - 正例：缓存结果由用户和项目共同确定，且二者之间没有实际父子层级时，将两者作为一个复合 key；读取和写入使用相同的业务身份。
    ```cpp
    using AllocationKey = std::pair<UserId, ProjectId>;
    std::unordered_map<AllocationKey, Allocation, AllocationKeyHash> mapOfAllocationByKey;

    const AllocationKey allocationKey{ userId, projectId };
    mapOfAllocationByKey.emplace(allocationKey, allocation);
    ```
  - 取舍：当外层对象确实拥有内层对象、两层容器直接反映该领域层级时，嵌套容器仍是合适表示；选择依据是业务关系，而非代码行数。

## 职责、所有权与复用

- **所有者职责**：业务职责所有者负责业务规则；状态所有者维护并修改唯一事实源、定义状态写入方式；生命周期所有者闭合创建、初始化、使用、失败恢复和释放。调用方只传递上下文并触发所有者提供的操作；不能为方便调用扩大成员或 setter 的访问范围，也不能让调用方依次拼装完整资源流程。

- 复用沿已确认的所有权和生命周期方向实现；不得仅为调用方便拆散所有者流程、反转引用方向、增加反向强引用或建立长期平行 cache。
  - 正例：多个调用方复用状态所有者提供的 `execute(context)`，由该入口统一维护状态和异常清理。

- **所有者边界内复用与适度抽象**：先按已确认的职责和所有权寻找复用位置，再依次考虑删除、现有类型或函数、标准库、平台能力、已有依赖和最小新代码。只有在重复逻辑明确且抽象边界清晰时才新增函数、类、接口或依赖。新依赖、公共抽象、扩展点或基础设施需要说明必要性并获得许可；模块围绕清晰职责组织。

- 单一调用点的短薄封装直接内联。非必要不使用局部 lambda；局部 lambda 仅限纯粹、无状态、仅服务当前翻译单元且不能用直接表达式清晰表达的短转换，声明与调用需要分开表达。涉及状态、生命周期或复用的逻辑优先由其所有者提供具名成员函数；纯粹、无状态且只服务当前翻译单元的转换可以使用 namespace helper。

- **创建期共享关系**：多个使用方需要共享同一业务对象时，在对象创建或装配阶段建立共同引用；后续流程通过对象身份使用该共享关系。业务标签仅用于创建期分组，不得在高频运行路径反复按标签查询、匹配或复制同一对象。
  - 正例：
    ```cpp
    auto pItem = std::make_shared<Item>(definition);
    firstConsumer.addItem(pItem);
    secondConsumer.addItem(pItem);
    ```

- **状态**：流程状态使用领域名称、枚举或类型，禁止使用无语义数字和字符串标记阶段。

## 数据与接口契约

- **数据流与契约清晰**：函数接收真实且有意义的数据，避免空参数、占位值、重复传递和相互冲突的数据来源。严格遵守既定字段、格式、接口、命名和 Schema；未经明确要求不增加隐式兼容、自动转换、别名匹配或猜测性处理。

- **参数语义**：状态参数必须明确表示最终值、增量或覆盖值；默认值须有明确业务含义，不能假定零值保留旧状态。参数语义会改变业务结果且尚未确定时，先确认契约再实现。
  - 正例：已定义为最终值的 `value` 使用 `m_value = value`；`Value()` 明确表示最终零值。

- **计算扩展与数据生效范围**：根据业务数据的生效范围选择实现方式。扩展现有计算时，默认在原本承担该职责的函数内修改，保留原流程、职责位置及默认调用行为；用户显式说明其他要求时，按其要求执行。需要支持本次计算的覆盖值时，默认采用可选参数：传入覆盖值时只返回本次计算结果，保持原有持久状态不变；未传入覆盖值时沿用原有取值和状态更新行为。先说明输入、返回结果和写回条件，再实施最小修改，并分别核查原值和覆盖值两条路径中的派生结果及状态变化。上述默认约定直接用于方案选择；发现现有契约或正确性要求无法满足时，说明具体冲突并取得用户对调整的明确确认。跨操作持续有效的数据根据已确认的共享需求确定保存位置与生命周期。按“最小实现的判断标准”比较原位置扩展、局部传值和必要接口调整的整体代价，提出足以覆盖当前验收条件的方案。

- **参数**：新增 CLI、API、配置或公开函数参数前取得用户授权；参数的必填或缺省语义依据已确认的业务和平台契约确定。布尔开关和模式参数各自表达单一、明确的职责。
  - 同一计算逻辑保持单一实现。接口由本次任务完整控制、默认值具有明确业务含义时，优先使用带默认参数的函数；公共虚接口或其他调用方需要保持兼容时，可以使用薄转发重载。选择前核对基类、派生类和调用方，比较两种方式的实际影响范围。已有公开签名的修改按用户明确授权执行。
    - 默认参数示例：接口可统一调整时，使用 `create(value = Value())` 表达已确认的缺省行为。
    - 转发重载示例：保留原公共虚接口，在特定实现中增加带参入口并复用同一份计算逻辑，使其他实现继续使用原接口。

- **参数载体类型保持一致**：参数类型与其来源成员变量或调用方持有对象的表达类型保持一致，包括值、引用、裸指针、智能指针和指针层级；不为适配参数主动转换载体类型、包装智能指针或显式解引用。被调用方只读取或不保存对象，不构成改变载体类型的理由。
  - 参数只读时必须使用 `const`，并将 `const` 应用于实际不允许修改的层级；该规则适用于值、引用、裸指针、智能指针及其他参数载体。
  - 只有既有外部 API 已固定签名，或用户、项目契约明确规定所有权转移、生命周期或平台接口必须使用其他类型时，才按该明确契约例外处理；不能仅根据“函数不保存对象”推断为引用参数。
  - 正例：`Model* pModel = getModel();` 配套 `void build(Model* pModel);`，调用 `build(pModel);`。
  - 正例：`Model& model = getModel();` 配套 `void build(Model& model);`，调用 `build(model);`。
  - 正例：成员变量为 `std::shared_ptr<Model> m_pModel`，配套 `void build(std::shared_ptr<Model> pModel);`，调用 `build(m_pModel);`。
- **参数传递不创建无语义包装**：调用方已有值可由目标参数类型无损隐式构造时，直接传递该值；不得仅为匹配参数类型创建一次性包装局部变量。局部变量承载计算、校验、复用、生命周期或独立领域语义时保留。
  - 正例：`void setIndex(std::optional<size_t> iIndex);` 配套 `const size_t iIndex = 1;`，调用 `setIndex(iIndex);`。

- **Schema**：当前确认的 Schema 是有效契约，旧字段、已删除字段和结构损坏的数据直接报错；迁移由单独批准的确定性脚本执行。

## 校验与错误处理

- **边界校验与错误暴露**：在外部输入、文件、网络响应和反序列化边界执行必要校验。非法输入和契约违反必须带定位信息暴露，宽泛捕获不得隐藏失败或返回伪造成功。错误的具体输出形式、异常类型、日志方式和降级策略依据项目契约或用户授权决定。

- 只校验不可信或类型无法保证的数据；
  - 正例：解析外部数组后检查元素数量；

- **对象发布前有效**：对象在首次向外部代码发布或使用前，必须处于目标有效状态并满足核心不变量。构造函数、工厂或局部组装流程可以在发布前分阶段完成身份、所有权和状态设置，但发布前必须完成必要校验；禁止发布半成品，或在发布后依赖外部 setter 修正关键业务状态。

- **对象自身校验与上下文约束的责任归属**：对象自身数据的有效性校验必须由对象内部在构造、赋值或状态变更边界完成；外部调用方不得代替对象检查或修正这类数据。只有依赖其他对象、外部配置或流程阶段才能确定的关系约束，才由掌握这些上下文的流程层校验。每条约束只保留一个校验责任归属，不得由多个层重复实现；失败时先记录上下文再抛出异常，校验未通过的对象不得返回、存储或交给其他代码使用。
  - 对象自身约束包括字段取值范围、非法哨兵值、成员组合关系和生命周期状态；
    - 正例：`Order` 构造函数拒绝负数量并保证对象发布前有效；
  - 外部上下文约束包括集合长度与外部配置的匹配、对象之间的兼容性和资源初始化顺序；
    - 正例：`BatchBuilder` 在获得批次容量后校验 item 数量，`PlanOptimizationImplementation` 在 shared beam geometry 建立后校验 `PatientData` ID vector 长度；

- 每次显式抛出或重新抛出异常前，必须通过现有 `g_logger`（或项目对应的 logger 实例）记录当前层的错误上下文；日志不能替代异常，logger 不可用时仍必须抛出异常。

- **日志修改范围**：先将用户要确认的信息与已有日志逐项对应，确定具体缺口；复用已有记录，只补缺失的信息，保持原业务判断和异常处理方式。
  - 正例：用户需要查看某个值修改前后的结果，已有日志记录了修改后的值，就只补充修改前的值。

## 代码组织与风格

默认沿用项目已有风格，具体形式遵循上级可读性原则。

### 命名与常量

- **命名服从职责边界**：成员、函数和类型的名称必须反映已经确认的业务职责、状态范围和生命周期边界。负责登记、持有、索引、分配或协调某类对象的通用状态，按该对象及其管理范围命名；下游特化场景、算法或消费者不得反向缩小该通用状态的名称，也不得用局部命名掩盖职责泄漏。
  - 正例：管理器维护 `entityIds`，各流程按该 registry 查询或分配对象。
- **迭代器与索引命名**：迭代器变量使用 `iter` 前缀并紧接被迭代对象的完整语义；索引变量使用 `i` 前缀并紧接被索引对象的完整语义。不得使用 `it`、`iter`、`idx`、`index` 等缺少对象语义的名称，也不得让 `i` 前缀变量承载迭代器。
  - 正例：
    ```cpp
    for (auto iterVoiOccupancy = pVoiOccupancy->begin(); iterVoiOccupancy != pVoiOccupancy->end(); ++iterVoiOccupancy)
    {
        const auto iVoxel = iterVoiOccupancy.GetIndex();
        pPropertyTags->setInTargetVolume(iVoxel);
    }
    ```

- **布尔变量命名**：布尔变量使用 `b` 前缀，并采用语义明确的命名。
  - 正例：`const bool bValueChanged = oldValue != newValue;`

- **常量**：协议和格式常量可以留在代码中；业务可变值来自业务事实源；算法阈值使用有来源的名称；物理数值保留校准入口。

- **常量作用域**：常量声明在全部使用点所需的最小共同作用域；仅服务一个函数或分支的常量不提升为文件级或类级状态。
  - 正例：const int hiddenObjectiveOffset = 1000000; 声明在使用它的函数内。
- **固定集合规模**：集合规模会在多个位置使用，或当前循环需要使用固定快照而不反映动态更新时，先以来源 API 的原始返回类型缓存为 `const` 局部变量，再用于 `reserve`、循环上界等操作。
  - 正例：`const int nRobustScenarioGroups = robustScenarioData.scenario_groups_size();`

### 控制流与表达式

- **循环结构与单一索引**：按索引遍历时，使用经典 for (初始化; 索引范围; i索引++) 形式；循环头只表达索引初始化、范围和递增。业务终止条件在循环体中显式赋值并 break，函数末尾统一返回结果。多个数据源表示同一业务对象时，用同一个扁平索引访问；需要按该索引读取的数据由其状态所有者提供 accessor，不维护平行索引或嵌套循环对齐。
  - 正例：
    ~~~cpp
    bool bHasIncludedRobustCostFunction = false;
    const int nCostFunctions = pReferenceCube->getNCostFunctions();
    for (int iCostFunction = 0; iCostFunction < nCostFunctions; iCostFunction++)
    {
        const auto& costFunctionDNA = pReferenceCube->getCostFunctionDNA(iCostFunction);
        const auto costFunctionInterface = pReferenceCube->getCostFunctionInterface(iCostFunction);
        const auto costFunctionState = pReferenceCube->getCostFunctionState(iCostFunction);
        if (isCostFunctionIncluded(costFunctionInterface, costFunctionState, costFunctionDNA, includeOffCf) && costFunctionInterface.isRobust())
        {
            bHasIncludedRobustCostFunction = true;
            break;
        }
    }
    return bHasIncludedRobustCostFunction;
    ~~~
  - std::any_of 和局部 lambda 只用于天然单一集合上的纯粹、无状态判断；lambda 不得捕获并修改索引、状态或生命周期对象。
    - 正例：return std::any_of(entries.begin(), entries.end(), [](const Entry& entry) { return entry.isRobust(); });
- **自增与自减副作用分离**：`++` 和 `--` 只能作为独立语句，或用于经典 `for` 循环头中的单一索引递增；禁止在赋值、函数参数、返回值、条件、容器操作或其他表达式中使用其结果。读取当前值和修改变量必须拆成顺序明确的独立语句。
  - 正例：
    ```cpp
    mapping.at(iVoxel) = nMappedVoxels;
    nMappedVoxels++;
    ```

- **统一正常返回值**：函数的多个正常控制分支产出同一语义的返回值时，先声明具有领域语义的局部返回值，各分支负责赋值，函数末尾统一 `return`。异常路径继续直接记录并 `throw`；不以默认值掩盖未赋值分支。
  - 正例：
    ```cpp
    int beamNumber;
    if (bUseFirstBeam)
    {
        beamNumber = 1;
    }
    else
    {
        beamNumber = 2;
    }
    return beamNumber;
    ```

- **三元与 `if/else` 的可读性偏好**：简单、清晰的值选择优先考虑三元；需要展示多个动作、错误处理或复杂控制流程，分支包含校验、日志、状态修改等多个步骤，或嵌套条件掩盖业务含义时，优先使用 `if/else`。

  - 函数调用或判空后的安全解引用本身，不作为禁止三元的理由；条件与两个结果的关系直观、求值安全容易判断时，可以使用三元。
  - 业务前提不明显时，用简短注释说明前提及其含义；如果表达式需要反复拆解才能看懂，优先展开为 `if/else`。
  - 适合三元的例子：`const auto value = bUseFirstValue ? firstValue : secondValue;`。
  - 对 `pGroup == nullptr ? nullptr : pGroup->preparedData.at(index)` 这种“对象可能不存在，存在时再访问内部数据”的表达，更推荐显式 `if`，让存在性判断和数据访问分开呈现；不因表达式较短就推荐三元。这个偏好不扩展为对所有指针访问的统一禁令。

### 对象与容器操作

- 对象构造与容器操作分开表达：对象需要通过构造函数、工厂函数或复杂表达式生成时，即使可以原位构造，也先用局部变量完成构造，再执行 `emplace`、`insert`、`push_back` 或其他容器操作；构造和容器操作不得合并为一行。该规则只统一可读性，不改变所有权或异常语义。普通函数调用中的直接值或空容器参数可直接传递，无需仅为传参创建无独立语义的局部变量。
  - 正例：
    ```cpp
    auto item = createItem(input);
    items.push_back(item);
    ```
- **容器元素访问**：对于提供 `.at()` 的容器（如 `std::vector`、`std::array`、`std::deque`、`std::string`、`std::map` 和 `std::unordered_map`），读取或更新已有元素时必须使用 `.at()`，不得使用 `[]` 绕过边界检查。
  - 正例：`const auto& value = values.at(index);`、`mapping.at(key) = value;`
  - 例外：关联容器的 `[]` 仅用于明确需要键不存在时插入默认值的场景，例如 `mapping[key] = value;`；原生数组、指针及不提供 `.at()` 的类型不适用本规则。

### 注释与排版

- **既有注释保留**：修改代码时保留已有注释。实现变化使注释不准确时，更新为准确表述，并保留其中仍有效的业务背景、约束和失败语义；删除已有注释须用户明确授权。
  - 正例：将 `// Register only after all scenario mappings are validated.` 更新为 `// Publish only after all beam-instance mappings are validated.`，保留“校验完成后才发布”的约束。
- **注释换行语义**：注释按完整语义单元换行。完整句子、独立分句或明确的逻辑转折可以各占一行；不得仅为控制行宽而在同一语义单元中间换行。注释行末不得含空白字符。
  - 正例：

    ```cpp
    // PatientData 0 is the single plan reference context.
    // The other PatientDatas keep the same objective layout for index and state alignment,
    // but they must not contribute to a non-robust objective.
    ```

- 单行强制：代码中的声明、表达式、调用、参数、元素或字段能清晰地写在一行时，必须保持单行；不得仅因参数、元素或字段较多而换行。注释不适用本规则。
  - 正例：`void update(Value value, Input a, Output b, Content c, Rules d);`。

- 大括号风格：所有左大括号必须移动到下一行，采用 Allman 风格；适用于命名空间、类型、函数、控制语句、lambda 以及其他代码块。右大括号与所属代码块保持对应缩进。
  - 正例：
    ```cpp
    const auto item = std::find_if(items.begin(), items.end(), [id](const auto& value)
    {
        return value.id == id;
    });
    ```

### 头文件与行尾

- **头文件默认只放声明**：普通非模板函数在头文件声明、对应源文件定义；短 getter 也遵循该规则。模板、必须在使用点可见的 `constexpr`，以及明确采用 header-only 契约的代码可以在头文件定义。

- **公共类型依赖**：由共享公共头单点提供，下游不得重复包含。
  - 正例：`model.h` 包含 `value.h`，`model.cpp` 和 `view.h` 只包含 `model.h`。

- **行尾格式**：C、C++、C# 代码文件统一使用 CRLF（`\r\n`）作为行尾，禁止混用 LF 与 CRLF。

- **行尾规范化工具**：补丁、格式化或批量改写后，对本次受影响的 C、C++、C# 文件在差异检查前运行一次；脚本仅在需要时按字节规范化行尾，保留其他内容和编码。
  - 规范化本次明确修改的文件：
    ```powershell
    & "$env:USERPROFILE\.codex\tools\Normalize-TextEol.ps1" -Path $paths
    ```
  - 只检查、不写入：
    ```powershell
    pwsh -NoProfile -File "$env:USERPROFILE\.codex\tools\Normalize-TextEol.ps1" -Path $paths -Eol CRLF -Check
    ```
  - `$paths` 只包含本次明确修改的文件；不得自动规范化所有 Git 改动，避免影响脏工作树中的无关更改。
